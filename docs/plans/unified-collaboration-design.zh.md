## 产品目标

用户通过一个主对话推进项目，随时查看任务进度、参与成员、独立执行记录和产物。简单工作由当前智能体直接完成；用户开启协作后，复杂工作可以分派给多个成员。成员数量和层级随实际任务需要确定。

子智能体、团队、任务分工共用执行基础。临时子代理独立可用；团队在子代理运行时之上管理角色、共享任务和统一控制。

## 概念与职责

| 概念 | 职责 | 生命周期 | 用户界面 |
| --- | --- | --- | --- |
| 主对话 | 接收目标、澄清需求、汇总结果和交付 | 可跨越多次任务执行 | 当前对话 |
| 任务 | 定义要完成的工作、依赖、验收条件和产物 | 从建立到验收、取消或阻塞 | 协作面板的任务视图 |
| 成员 | 在独立上下文中执行分配的工作 | 一次或多次受控执行；闲置时不调用模型 | 协作面板的成员视图和独立对话 |
| 协作方案 | 保存角色、模型、工具、范围、预算及派工规则 | 持久配置，启动任务时形成快照 | 设置中的协作方案 |
| 调度器 | 根据依赖和事件派工、记录状态、控制重试和停止 | 随一次任务执行存在 | 通过任务进度体现 |

“临时子代理”表示主智能体按需委派的执行者，不要求创建团队或开启团队模式；是否可用仍由当前智能体的工具和权限决定。“团队成员”表示纳入协作方案和共享任务管理的子代理。“分工”是把任务分配给执行者的操作。

关闭团队模式不移除独立委派工具，也不隐藏既有子代理记录。临时子代理保留独立上下文、模型和执行记录；可继续模式支持独立续聊，一次性模式保留只读历史。角色的下级委派限制只约束该角色，不能替代全局子代理设置。

一个任务可以经历多个尝试，每个尝试只有一个执行者。多个成员参与同一目标时，拆成可验收的子任务。重试或换模型产生新尝试，保留原来的日志、产物和失败原因。

## 默认执行方式

1. 当前智能体负责理解目标、必要的规划和最终汇总。
2. 调度器读取依赖关系，派发已经可以执行的子任务。
3. 成员使用独立上下文，获得目标、相关文件、约束和验收条件。
4. 完成、失败、审批和取消事件触发状态推进。
5. 结果满足验收条件后才将任务标为完成；达到返工上限则明确受阻。

默认不固定创建规划者、主管、执行者三层模型。需要独立复核的方案可以增加审查角色；实际执行前按依赖启动所需成员。成员等待消息、依赖或审批时由调度器等待事件，不反复调用模型查询状态。

## 界面入口

模型选择左侧保留一个“协作”入口，提供以下选择：

- 单人：当前智能体推进任务，可以维护任务清单，并在工具和权限允许时临时委派子代理，无需配置团队。
- 自动协作：用户明确开启后，按任务需要创建成员，受方案中的并发、工具和预算限制。
- 自定义方案：选择已保存的角色和模型配置，按需实例化成员。

标题栏显示协作摘要，点击打开同一个面板。任务视图包含依赖、执行者、进度、审批、验收和产物；成员视图明确显示临时子代理入口及团队成员，包含模型、职责、当前任务、状态、用量及独立对话入口。设置中明确保留临时子代理设置；关闭团队功能时这些入口仍可访问。

全局设置分为功能可用性、默认模式和方案管理。当前会话模式即时保存；运行中的任务保持配置快照，修改默认设置不悄悄影响正在执行的成员。

## 独立对话与控制

- 主对话接收目标调整、统一停止和最终结果。
- 成员对话可查看执行过程，也可直接发送补充要求；输入区域始终明确接收成员与所属任务。
- 发给成员的补充要求写入同一执行消息队列，并同步可追溯的任务事件，不能额外启动一个并发执行循环。
- 用户直接修改任务约束后更新任务版本，旧版本结果不能自动通过验收。
- 停止成员只影响对应执行及其后代；停止主任务取消全部后代、待执行工作和待审批请求。
- 无所属任务的长期独立对话通过明确的解除关联操作建立，原任务保留交接状态。

## 统一状态与权限

任务、成员、消息和审批引用同一执行标识，避免多个面板各自维护互相矛盾的状态。任务状态为待处理、可执行、执行中、等待审批、待验收、完成、受阻和取消；成员状态从所属执行推导。

实际工具权限、写入范围、停止传播和预算限制由执行层控制。角色文字、任务标题和任务板的 writeScopes 只表达意图，不能替代权限校验。

成员有效权限取父任务可委派权限与角色配置的交集。主任务对某次越界调用的批准不自动授权其他成员；审批保留发起成员、所属任务、目标路径和具体调用。更换模型或重试时重新计算有效权限。

并行写入先检查范围冲突：独立目录可并行，重叠文件串行，支持 Git 的项目可以使用隔离工作树。合并与验收是可观察的任务阶段。

## 自动化与复用

手动发送、定时触发和外部事件均可以启动同一任务执行模型。自动化保存触发条件、任务目标和协作方案引用，运行时生成配置快照；不另外实现成员管理、审批或任务调度。

## Token 开销与对照验收

协作不保证节省 token。独立上下文和定向交接可以减少无关历史的重复输入；成员初始化、协调消息、重复阅读、审查与返工都会增加开销。简单任务优先由主智能体完成，临时独立工作按需委派，具有明确依赖与并行收益的项目再使用团队方案。

成本优化采用最小充分上下文、明确的任务边界和按需启动；等待依赖、消息或审批时不通过反复模型调用轮询。不能为降低 token 数量省略必要验证或接受未完成结果。

对照使用相同任务、输入文件、验收标准和可比较的模型设置，分别执行单 Agent 与团队方案。统计主智能体、全部成员、协调、失败重试和返工的总输入与输出，同时报告完成质量、人工介入次数和耗时。缓存命中单独列示，并按提供方计量口径归一，避免与输入 token 重复累加。费用根据实际可知单价计算；未知价格保持未知。

只有达到相同验收条件后，才比较总 token 和费用。缓存折扣导致费用下降，不代表 token 数量同步下降；并行耗时减少也不代表 token 节省。尚无真实项目对照数据时，不发布节省百分比。

## 实施边界

第一阶段完成一个协作入口、统一任务状态、成员独立对话、基本方案配置、明确的审批归属以及递归停止。执行结构默认保持一层负责人和成员，成员数量有上限。

后续阶段增加复杂依赖、独立审查、有限返工、隔离工作树和自动化触发。递归成员、多层管理者、成员间自由通信和自动模型升级放在明确需要这些能力的方案中。

底层逐步收敛为任务执行、成员执行、协作配置三类服务。现有 agent_team 与 subagent 工具可以先作为兼容接口复用统一服务，禁止同时启动两套调度器。既有成员会话和团队任务保留原始标识，通过映射迁移；孤立记录明确标为历史记录。

原有按钮位置、多方案、自定义角色、独立对话、模型路由、上下文隔离、预算和发布要求继续保留。固定三层分工从默认行为调整为可选方案。新的交互设计确定前不增加并列功能入口。
