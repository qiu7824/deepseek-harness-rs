# 工具发现、运行环境与执行可靠性统一修复方案

状态：部分实施，尚未完成全量验收及新版发布。2026-09-17 复核基线为 `e7bafb32f0`，分项进度见第 23 节；本文描述的目标能力不能直接视为已交付功能。

## 1. 目标与范围

将工具发现、环境诊断、执行配置、沙箱授权、错误恢复和产物验收连接成一条可追溯链路。用户能够选择合适的运行环境，Agent 能够获知实际能力和边界，并在失败后给出正确的下一步。

主要质量目标：

- 关键步骤失败后，不执行依赖该步骤的写入或交付；后续成功不能覆盖已发生的失败。
- 找不到命令、权限不足、控制台异常、DLL 装载失败、输入损坏与程序逻辑错误分别报告。
- 宿主已安装不等于沙箱可运行；工具被发现不等于获得调用权限。
- 缓存命中减少探测开销，不替代实时授权检查。
- 用户选择可见、持久且可撤销；运行中的任务不被静默切换环境。
- 前台、后台、持久终端和远程执行共享结果契约，平台差异明确展示。

本文完整定义工具目录、自动发现、会话加载状态、环境按需探测、缓存失效、配置与验收，不依赖另一个方案补充实现要求。[工具发现与运行环境能力管理](tool-discovery-and-environment-cache.zh.md) 保留为基础设计记录。故障验收依据 [执行链路审计](windows-execution-agent-bug-audit.zh.md)、[业务会话归因](session-09334282-execution-root-causes.zh.md) 和 [跨平台回归](execution-cross-platform-audit.zh.md)。

## 2. 用户设置：简单默认，必要时可精确选择

设置入口为“设置 → 工具与运行环境”；会话顶部显示简短环境状态，可为当前会话覆盖默认选择。

| 设置 | 用户选择 | 推荐默认 | 生效范围 |
|---|---|---|---|
| 执行方案 | 自动推荐、手动指定 | 自动推荐 | 全局默认；支持项目、会话覆盖 |
| Shell | 检测到的 PowerShell 7、Windows PowerShell 5.1、Bash、Zsh、显式路径 | Windows 优先验证通过的 PS7；Unix 优先验证通过的原生 Shell | 下一次执行；既有终端需重建 |
| Python | 项目虚拟环境、托管环境、宿主已安装解释器、显式路径 | 已信任项目配置，其次通过验证的托管/宿主解释器 | 项目优先，会话可覆盖 |
| Rust/Node 等工具链 | 自动发现、固定版本或路径 | 自动发现并验证 | 项目或会话 |
| 权限模式 | 仅查看、工作区保护、完全访问 | 工作区保护 | 复用现有权限服务 |
| 沙箱实现（高级） | 自动、已交付且通过验收的实现 | 当前平台验证通过的实现 | 受部署策略约束；更换需重建相关进程 |
| 额外目录 | 添加、查看、撤销；区分读和写 | 无额外写目录 | 单次、会话或显式保存的规则 |
| 工具展示 | 按需加载、全部展示 | 按需加载 | 模型声明，不改变执行权限 |
| 环境缓存 | 复用、刷新所选项、清空诊断缓存 | 复用有效缓存 | 当前环境；不会清除用户依赖 |
| Office 转换 | WPS 自动定位、指定 WPS 路径 | WPS | 全局或项目 |
| 执行后端 | 当前本机，以及已连接且完成验证的后端 | 本机 | 会话固定 |

远程、WSL、容器和替代 Windows 沙箱实现仅在适配器已交付并通过验证时出现为可选项；未实现的能力不显示成可用开关。Windows/Linux/macOS 可选项由本机事实生成，不展示不适用的程序名称。

“兼容性”与“权限”是独立维度。选择 PS5、Git Bash、另一 Python 或容器不自动开启完全访问；模型不能在重试时自行修改用户的权限模式。

“完全访问”仅表示解除产品对应的沙箱限制，不表示获得操作系统管理员身份，也不能绕过部署策略。沿用现有审批策略，不把权限模式与每条命令是否询问强行绑定。

### 2.1 用户交互

普通用户只需看见：当前方案、解释器、权限模式，以及“检查环境”“刷新”“切换”操作。高级设置才展示路径、缓存时效和工具声明预算。

默认自动模式完成按需工具加载、首次必要探测、有效缓存复用、相关缓存失效、能力摘要注入和会话恢复。用户不需要先打开设置页、点击“检查环境”或手动刷新才能完成普通任务；这些按钮只提供查看与主动干预入口。手动指定解释器或 Shell 仅固定候选选择，不关闭自动发现、缓存复用和执行验证。

每个候选环境显示独立状态：“已定位”“宿主可运行”“当前工作区可运行”“尚未验证”“缺少依赖”。不得把发现一个 exe 显示成“全部功能正常”。

保存前提供有界检查及失败原因。指定环境不可用时保留用户选择并明确阻塞，不悄悄使用另一解释器。自动模式只能在受信任候选中、相同权限约束下选择替代环境，并在执行前记录实际选择。

用户可以选择“本次使用”“仅此会话”“设为项目默认”或“设为全局默认”。项目文件中的偏好不授予额外权限；不可信项目不能通过配置指定执行任意初始化脚本或扩大目录范围。

已授权范围内的常规操作不重复询问。只有新增的权限缺口才进入现有授权通道；策略不允许询问时显示明确原因，不生成无法执行的提权建议。

### 2.2 运行中的任务

- 新偏好对后续执行生效；正在运行的任务保留原环境快照。
- 切换环境时明确哪些持久终端需要重建；旧终端不得冒充新环境。
- 权限收紧或授权撤销必须使相关持久进程失效并按既有生命周期机制停止，不沿用更宽权限的旧终端。
- 撤销效果与失败状态需要反馈；不能只更新 UI 标签而留下旧权限进程。
- 刷新诊断缓存不会停止任务，也不会删除虚拟环境、包缓存或项目文件。

## 3. 自动工具发现与会话上下文

继续使用原始 ToolRuntime 注册表作为唯一工具定义和作用域依据，复用 `tool_search`、`tool_describe`、`tools/discovery` 事件和现有预算规则。

| 层 | 回答的问题 | 不能推导的结论 |
|---|---|---|
| 工具注册与作用域 | 这个工具是否允许此 Agent 调用？ | 外部程序已安装 |
| 工具发现 | 模型是否已获得工具声明？ | 获得额外文件或网络权限 |
| 宿主环境缓存 | 主机上定位到了什么程序及能力？ | 当前沙箱、虚拟环境或远端也能使用 |
| 执行环境验证 | 所选环境能否完成指定能力探测？ | 允许访问任何输入或输出路径 |
| 执行授权 | 此次对象与操作是否被允许？ | 操作已经成功 |
| 产物验收 | 目标结果是否达到任务要求？ | 可以省略原始退出状态和错误记录 |

推荐保留现有工具预算：eagerLimit=32、listingChars=4096、maxLoaded=96、maxSchemaBytes=131072；属于可调默认值，不作为安全边界。核心发现入口、环境诊断及必要执行工具保持常驻；新增执行工具需要计入总声明预算。

搜索无结果仍提供允许范围内的来源与精确名称恢复路径。缓存、会话恢复、分叉和上下文压缩后重新核对工具摘要、版本和权限；聊天文字、模型总结与搜索内容不得写入可信能力状态。

代码模式和普通 function 模式共用执行授权；原生工具声明裁剪不削弱代码模式原有边界。

### 3.1 目录装配与渐进披露

1. 从当前作用域允许的 ToolRuntime 注册表建立目录；先做权限过滤，再搜索、计数和展示，不泄露禁止工具的名称或来源。
2. 核心工具与发现入口直接可用。小目录中的普通工具保留直接调用；MCP 默认延迟加载；目录超过 eagerLimit 时，非核心工具转入检索目录。
3. 清单按来源组织，并在 listingChars 内依次降级为“简述 → 名称 → 来源计数”；在完整 UTF-8 边界截断，明确展示省略数量和继续发现入口。
4. 用户不需要逐个勾选常用工具。模型遇到未加载能力时调用常驻发现入口，获得声明后继续执行；不每轮按用户消息关键词重新裁剪全部工具。
5. 参数声明完整性不可破坏：不能为了凑预算截断一个 JSON schema。核心工具或单项超预算定义按现有直接可见策略处理，同时检查模型提供方总请求预算；超过其硬限制时报告具体限制，不发送损坏的请求。

### 3.2 一次搜索即可准备调用

`tool_search` 在允许目录内按名称、来源和描述本地检索，精确名称优先，兼容中文描述和词汇差异。命中结果同时返回完整参数、工具来源和激活状态，并激活预算内的匹配项；下一次模型工具调用即可使用，不强制增加一次 tool_describe。

已知名称通过 `tool_describe(names=[...])` 直接加载；`release=[...]` 显式释放旧定义。不因每轮关键词变化自动淘汰已加载工具，避免反复搜索和声明缓存抖动。

搜索无匹配只表示当前查询未命中，返回允许范围内的可用来源及精确名称恢复方式，不表述为“系统没有这个能力”。达到加载预算时列出 overBudget 和未激活原因，允许释放旧项后继续；“搜索命中”与“已激活”分别返回。

### 3.3 自动更新与状态恢复

工具装配和实际执行两个时点都重新应用作用域、注册版本和权限。卸载或权限撤销立即使其不可调用；参数定义变更后旧摘要失效，返回需要重新加载的新定义，不能按旧参数继续执行。

加载结果由宿主写入版本化、非表面的 `tools/discovery` 事件，保存名称和声明摘要。不能从聊天文本、模型说“已加载”或压缩总结中恢复授权状态。

会话恢复与上下文压缩后自动恢复已加载工具，再核对当前注册表、摘要、预算和作用域。分叉只继承分叉边界内的发现状态，并应用子作用域过滤；父会话可见不代表子会话可以调用。

默认会话内存缓存最多 64 项，冷恢复最多检查最近 8192 个事件；已加载数量与 schema 字节预算分别受 maxLoaded 和 maxSchemaBytes 约束。超过恢复窗口又无有效快照时，明确返回需要重新按名称加载，不猜测历史。活跃会话在状态更新时保存有界快照，减少冷恢复扫描。

### 3.4 模型协议与代码模式

通用提供方继续使用普通 function schema；发现结果激活后，下一次请求的工具声明发生一次受控更新。工具集变化可能使提供方前缀缓存失效，稳定后保持相同排序和声明，不每轮改写。不能宣称这一机制等同于 Responses 的追加式工具加载，也不能保证所有提供方节省相同 token 或费用。

代码模式保留既有完整工具绑定与执行边界，发现入口可通过 `run_code` 中的 `tools.tool_search`、`tools.tool_describe` 调用。原生模式延迟展示不额外限制代码模式原本已允许的调用；两者实际执行仍以同一作用域与权限服务为准。

### 3.5 工具加载自动化的边界

自动搜索和加载只准备工具声明，不自动安装插件、连接外部账号、取得凭据或执行外部写操作。缺少连接、插件或权限时返回相应状态；已经授权且已连接的工具可继续原任务，不为了正常的声明加载反复询问用户。

## 4. 统一执行环境描述

新增 EnvironmentProfile，以稳定 ID 和 revision 表示用户的环境选择；每次执行解析为不可变 ExecutionContext。

```text
EnvironmentProfile
  id, revision, scope, selectionMode
  backendRef, shellRef, pythonRef, toolchainRefs, officeProviderRef

ExecutionContext
  contextId, profileRevision, hostId, backendId, environmentFingerprint
  os, arch, cwd, shellPath, shellVersion, interpreterPaths
  permissionRevision, effectivePolicy, runtimeGrantRevision
```

字段是内部契约设计，最终名称通过版本化 API 确定。偏好描述和权限事件分别保存，避免环境配置文件成为授权入口。

普通偏好优先级：会话覆盖 > 用户认可的项目配置 > 全局偏好 > 平台默认。权限始终经过部署上限、当前会话策略与合法授权规则求值；上述偏好顺序不能覆盖权限上限。

Windows 自动模式优先 PS7，但必须通过受限启动、argv、模块、stderr、退出码和取消测试；仅检测到路径不能自动迁移。Linux/macOS 的原生 Shell 支持需完成 Host 工具装配，不能只修改可执行文件名。

现有 `pwsh` 工具保持 PowerShell 语义，不能在用户选择 Bash 后把同一条 PowerShell 字符串交给 Bash。原生程序优先走新增结构化执行入口；脚本通过对应语言适配器执行。

## 5. 两级能力缓存与渐进探测

保留现有 Host `environment_probe`，按固定能力目录探测；在其上增加“所选执行环境验证”，不让模型提交任意 probe 脚本。

基础能力目录完整保留 Python、Node、Git、ripgrep、PowerShell、FFmpeg 和 WPS；Rust 等通过受控的能力目录扩展加入。记录包含环境指纹、程序文件身份、检查时间、版本、状态、检查级别及有界错误信息。状态至少区分 ready、located、missing、permission_denied、timed_out、error、unknown；未知和取消均不当作缺失。

### 5.1 检查级别

| 级别 | 示例 | 触发方式 |
|---|---|---|
| locate | WPS 安装路径、python 可执行文件 | 按需；优先配置与注册信息 |
| launch | 在宿主或指定沙箱运行版本命令 | 用户检查或任务首次需要 |
| dependency | 指定 Python 中 import fitz、Rust 工具链依赖 | 任务确实需要该模块时 |
| feature | 解码小型测试图、转换内置最小文档、离线编译小程序 | 独立有界检查，使用托管测试文件 |

所有主动检查都经相应执行环境与授权机制。Office 首次定位不启动 GUI；文档导出验证通过明确的 WPS 自动化通道，不能把任意 COM 激活混入轻量发现。

Python 的 find_spec 只说明模块可定位。导入能力需使用所选解释器另测；包版本、DLL 依赖及功能分别记录。宿主隔离模式探测不能冒充项目虚拟环境结果，也不能把项目中同名模块的影响隐藏掉。

固定命令仍可能启动被替换的程序或项目初始化逻辑，因此候选程序来源必须受信任；自动探测不执行仓库提供的 profile、任意工具脚本或整个依赖安装过程。

### 5.2 缓存键和失效

宿主缓存键包括 hostId、用户身份、OS/架构、环境配置和 PATH 指纹、程序身份。执行环境缓存额外包含 backend/image 身份、profileRevision、权限 revision、运行时授权 revision、项目虚拟环境和必要 cwd/config 指纹。

不同沙箱、用户、主机、项目虚拟环境及远端禁止混用“可运行”结论。权限检查不缓存为长期允许；每次实际执行重新授权。

沿用现有 Host 成功/已定位最长 24 小时、失败最长 60 秒、持久缓存 128 KiB 的基础规则。新增环境可运行性检查建议默认最长 5 分钟，且权限或配置变化立即失效；它不是安全授权缓存。具体时效通过性能验收调整。

程序身份、包根目录状态、设置、镜像、权限、工作区配置和时间异常会使相关结果失效。仅依赖目录 mtime 不能保证检测到全部包内文件替换；显式安装/更新事件、运行失败及周期性验证共同补足。安全相关执行不能只相信缓存中的 size/mtime。

同键并发探测合并；取消只取消对应调用等待或无人使用的探测进程，不把取消结果保存为“缺失”。共享探测需引用计数，不能由一个取消请求终止其他正常等待者。refresh 使旧代结果失效，迟到的旧请求不得覆盖新代结果。

失败按类短期缓存。一次真实执行失败只刷新相关解释器、模块和环境，不清空所有能力缓存。恢复后立即清除旧失败状态。

持久化使用版本化、原子写入和确定大小上限；损坏缓存可重建。输出不包含凭据、完整 PATH 或原始环境变量；模型只接收当前任务必要的允许能力摘要。

### 5.3 自动触发与执行时序

| 触发点 | 自动动作 | 不应发生的动作 |
|---|---|---|
| Host 启动 | 读取并验证有界缓存、配置和注册目录；损坏缓存忽略并记录状态 | 全盘扫描、检查所有程序、因坏缓存阻止会话启动 |
| 新任务首次需要某能力 | 先查当前环境对应缓存；未命中时仅探测该能力的最低必要级别 | 每个任务重新扫描全部软件 |
| 每次模型请求装配 | 注入有效且有权限的缓存摘要与明确配置路径 | 为生成上下文启动探测进程 |
| 同任务再次需要相同能力 | 复用有效记录及已选环境引用 | 反复 Get-Command、pip list、全盘搜索 |
| 实际执行失败 | 按类别使相关记录失效，必要时补一次有界诊断 | 全部缓存清空、无条件重试或安装依赖 |
| 配置、程序、包或权限发生变化 | 增加相应 generation/revision；后续按需重测 | 在旧权限结果上继续标注可运行 |
| TTL 到期 | 记录过期；下一次确实需要时重新检查 | 每轮或后台轮询所有过期能力 |
| 用户点击刷新 | 刷新所选能力/环境，合并并发请求并显示进度 | 擦除用户虚拟环境、清理项目文件 |
| 会话恢复、分叉、压缩 | 恢复发现快照；能力记录按环境和权限重新校验 | 把旧会话的宿主能力套到新远端 |

确定性自动预检由执行工具声明的依赖、所选程序引用或明确能力请求触发。临时 Shell 脚本的需求不能通过随意解析源码推断；模型在首次需要时调用 environment_probe，后续使用结果。调度器和模型共用同一探测缓存与并发门，不能形成两套重复检测链路。

探测阶段若确有权限缺口，通过既有策略处理。允许范围内自动检查，不为了缓存未命中增加额外确认；未知能力、GUI 启动、软件安装和账号连接不伪装成无副作用探测。

### 5.4 自动上下文与失败恢复状态机

```text
任务需要能力
  → 检查已加载工具与允许目录
  → 必要时一次搜索/精确加载
  → 查询所选环境的能力缓存
  → 命中：复用；缺失/过期：有界按需探测
  → 解析实际执行环境并检查权限
  → 执行与验证
  → 失败：分类、失效相关记录、诊断后选择恢复动作
  → 成功：保存有效能力事实与产物校验结果
```

系统自动提供短摘要，例如“Python 路径与版本已确认，fitz 在当前解释器导入失败；WPS 已定位、转换功能未验证”。摘要保留作用域和检查级别，不把缓存中的路径伪装成永久可访问路径。

默认无需用户逐项操作。自动模式也不承诺所有故障都能自行修好：权限被拒绝、软件确实损坏或缺少用户选择时，应明确停止依赖步骤并给出具体处理入口，不能靠反复工具调用制造进展。

### 5.5 自动化效果与可观测性

统一记录 searchHitCount、catalogCount、loadedCount、loadedSchemaBytes、cacheHit、probeDuration、probeProcessCount、coalescedWaiters、invalidatedReason，以及任务总耗时和模型请求次数。指标按会话/环境聚合，不含凭据与完整命令敏感内容。

至少比较冷启动、热缓存、多轮重复使用、会话恢复和故障恢复五种场景。有效缓存命中应为零探测进程；相同能力连续使用不再次搜索；环境变更只触发受影响项。token/缓存收益以提供方实际用量和账单为准，工具声明字节数仅作为本地诊断指标。

## 6. 可靠的执行与失败传播

### 6.1 原生程序执行

新增结构化原生执行工具，参数包含程序引用、argv 数组、cwd、环境引用、超时和运行方式。Rust subprocess 直接构造参数，避免 Python `-c` 再经历 PowerShell 的二次引号解析。

复杂 Python 程序写入受管理脚本文件后执行；脚本作为数据传递，不拼成多层 Shell 字符串。Windows .bat/.cmd、自定义参数解析器和 Shell 内建命令使用独立适配器，不宣称一个 argv 编码器能覆盖所有程序。

基础结果始终保留原生退出码。业务执行默认要求退出 0；探测允许非零时返回“诊断结果”，不把它改写为业务成功。grep 无匹配、diff 有差异等只在已知命令语义下解释。

### 6.2 Shell 脚本与步骤

- 去掉没有实现保证的通用 `Commands fail fast` 声明。
- 对关键流程使用步骤级执行，某一步失败后不调度依赖步骤；保留每一步原始退出状态。
- PowerShell 采用经过验证的非交互初始化，关闭进度绘制；区分原生 stderr 与 PowerShell 错误记录。
- PS5 作为显式兼容选项，显示功能限制；需要可靠原生参数或失败传播时使用结构化入口。
- Bash/Zsh 以明确契约运行；不能仅靠 `set -e` 推断任意复杂脚本具备事务性。
- 显式处理的非零结果保持可观察；`allow_nonzero` 不恢复已经中断的脚本，也不代表所有子步骤成功。

设置选择解决环境差异，不能提供关闭错误校验、忽略全部 stderr 或隐藏失败的“兼容开关”。

## 7. 沙箱与工具链适配

延续现有权限模式和审批服务。AppContainer、Linux bubblewrap、macOS Seatbelt 各自提供实现，但必须暴露一致的能力与限制说明；不把完全访问包装成一般兼容模式。

Windows 可将 restricted token + ACL 作为后续兼容后端候选，但不纳入首批修复的可用承诺。交付前必须验证目录读写、原生 DLL、进程树、取消、网络与桌面边界，明确与 AppContainer 的差异。用户只能显式选择满足部署要求的后端；不能因某条命令失败自动退到隔离更弱的实现。优先完善 AppContainer 的运行时能力授权，再根据真实任务回归决定是否需要双后端。

Rust 工具链分开处理代理程序、已选 toolchain、运行库、链接器/SDK、registry/git 缓存和 target 输出。只授予必要的只读或执行路径，写入放在明确授权的缓存或工作区；禁止为方便而给整个用户目录开放权限。

Python 原生扩展同样区分解释器、模块、依赖 DLL 和缓存。出现 DLL 装载错误时先比较宿主与受限探测证据，避免宿主依赖本身损坏时仍反复提权。

WPS 从明确配置、宿主 App Paths 等可信安装信息中发现，返回真实路径与版本；发现结果不证明沙箱内 COM 可用。通过独立桌面操作通道执行授权的文档转换。

受限执行失败后，允许在同权限范围使用已验证兼容方案；需要新权限时申请最小目录和访问类型。若平台尚不支持该精度，明确说明限制，不伪装成已经实现的单文件授权。

## 8. 统一结果、错误与恢复

建议结果字段：

```text
executionId, executionContextId, phase
processState: starting | running | exited | cancelled | timed_out | failed_to_start
exitCode, nativeExitCode?, signal, commandStarted
stdout/stderr: preview, truncated, retainedRange, totalBytes, resourceId, complete
diagnostics[]: category, confidence, source, target?, operation?, rawCode?
effects: none | possible | verified
completion: running | succeeded | failed | unknown
retryAdvice: none | diagnose | same_policy_after_change | scoped_permission
```

Shell 最终退出码和原生子步骤退出码允许不同，均应保留。tool 调用成功只代表工具协议成功，不能代替子进程和产物成功。

分类使用可信运行器状态、结构化 Shell 错误及程序退出事实；应用 stderr 关键词只产生疑似线索。应用输出 `dsh-sandbox-windows:`、`bwrap:` 或 COM 示例文本不能直接变成运行器故障。

控制台异常、文件缺失、访问拒绝、DLL/依赖错误、参数解析、图片解码、数组运算、运行器启动、超时和取消分别处理。同一输出包含多个错误时保留多个诊断，不用整段文本的 COM 排除掩盖真实文件错误。

恢复顺序：确认阶段 → 最小只读诊断 → 刷新相关能力 → 同权限兼容恢复 → 必要授权 → 产物验证。任意重试都记录 parentExecutionId、已改变的条件和副作用检查结果；没有新证据不重复原命令。

超时和取消不提供事务回滚。已有输出、文件或外部效果必须先检查；安装、覆盖、删除和远程副作用不得通用自动重放。重试优先使用新的唯一候选目录。

## 9. 日志、PTY 与后台任务

原始 stdout/stderr 在收集端先进入有界持久流，再生成 head/tail 预览；不能先丢弃开头，再把剩余文本称为完整日志。超过磁盘预算时返回 complete=false 和丢失区间。

恢复 Node 同源的截断元数据与 spill 引用传递；前台、后台、任务完成通知和模型文本展示都保留这些事实。日志资源按 owner/scope 授权、限量保存，采用安全创建与明确过期机制。

PTY 输出静默只表示暂时无新输出。展示 waitReason、terminalState、observedExitCode 与 completion；缺少真实退出证据时为 unknown。完成帧必须与命令 ID 关联，不能匹配命令回显或窗口标题里的标记。

终端 cwd/env 属于该终端，独立进程使用自己的 ExecutionContext；跨工具交接显式传递 cwd。后台任务的“等待操作结束”不能渲染成“业务命令成功”。取消与退出确认覆盖进程树，结果不因稍后回调而从 cancelled 回写成 succeeded。

## 10. 图片与文档能力

提供可复用图片读写原语：Path 读取字节 → imdecode → 空值和形状检查；编码后通过受控路径写入。错误保留文件不存在、权限不足、空文件和解码失败的区别；不打印整个字节数组或像素矩阵。

图像合成先验证尺寸、通道、dtype、mask 广播规则。文档转换先确认 WPS 功能可用，再检查页数、页面尺寸、文字/表格布局和最终可打开性。普通 PyMuPDF 导入成功不等于 DOCX 渲染能力存在。

产物采用候选输出 → 内容/布局验证 → 版本检查 → 正式交付。尊重用户明确指定的 WPS 约束；不能因探测失败自动采用其他 Office 套件或未经验证的 HTML 重排路线。

## 11. 配置持久化与迁移

工具发现继续以现有 `tool-discovery.json` 为唯一配置所有者；当前启动读取机制必须如实显示“重启后生效”。后续热更新通过同一服务的版本化接口实现，不另外保存一份互相覆盖的 UI 配置。

默认启用有界自动发现，数据目录中的配置示例为：

```json
{
  "enabled": true,
  "eagerLimit": 32,
  "listingChars": 4096,
  "maxLoaded": 96,
  "maxSchemaBytes": 131072,
  "deferredPrefixes": ["mcp__"]
}
```

`enabled: false` 恢复全量原生工具声明，不关闭环境缓存、自动预检或权限检查；`eagerTools` 是高级覆盖选项，缺省使用核心工具集合。修改发现方式、手动指定运行环境和刷新能力缓存是三个独立操作，不共享一个含义模糊的“关闭自动化”开关。

环境缓存保存在宿主缓存目录；现有 v1 文件为 `environment-capabilities-v1.json`，有 schema 版本与 128 KiB 上限。所选执行环境缓存按新版本单独命名和迁移，不向任务工作区写缓存，不记录密钥和完整环境变量。

新增环境偏好接入现有 SettingsProvider，权限继续使用 permission 服务与会话事件。缓存只位于宿主/后端缓存目录，不能写入任务项目，也不能保存授权凭据。

会话保存 profile 引用、revision 和必要执行快照；恢复后核对主机、路径和权限，不盲目重放过期可运行状态。分叉继承偏好，不自动复制不可转移授权、运行中的终端或远端会话凭据。

迁移遵循：

1. 读取旧设置并保留原值；生成新结构时携带 schemaVersion 和来源。
2. 保留显式 Shell/解释器选择；旧版隐式 PS5 行为的迁移在下一次会话执行前展示差异。
3. 新环境未验证时保留可回退的旧配置，不静默升级权限或安装软件。
4. 配置原子提交，失败恢复 last-known-good；旧版仍能读取未迁移的发现文件。
5. 环境能力 v1 缓存只能恢复宿主检查事实，不能升级为沙箱可运行或 feature ready。
6. 配置回滚与代码回滚分开；不能为回滚兼容而重新启用已确认会隐藏失败的执行契约。

## 15. G03：任务级完成契约与验收

复用现有 goal、workflow、present、workspace_scratch 和版本化 promote；新增任务验收契约，不以另一个聊天总结替代检查器。

```text
TaskContract
  taskId, revision, objective, constraints
  steps[], expectedOutputs[], acceptanceChecks[]
  state: planned | running | validating | validation_failed |
         awaiting_user | completed | cancelled | blocked
AcceptanceResult
  checkId, checkerVersion, inputIdentity, status
  evidenceRefs[], coverage, failureReason
```

任务目标和约束来自用户授权范围；Agent 可以拆分步骤，但不能自行降低验收要求。普通问答不必制造文件产物，代码、文档、数据和交互任务使用相应验收类型。

检查器至少覆盖：代码构建/测试、文档可打开性和分页/布局、图片解码/尺寸/通道、表格公式和数据约束、服务健康检查。文件存在、进程退出 0 和模型说“已完成”不能单独满足业务验收。

完成条件由契约判定：必要步骤和可自动验证的要求全部通过，必要产物已按版本检查交付，未遗留要求收集的后台任务；需要用户验收时进入 awaiting_user，未知项说明覆盖范围。人工确认仅在任务实际需要时请求，不给常规可自动验证操作增加确认流程。

对敏感或无法自动证明的内容保留明确的未验证状态。检查器版本、输入摘要和证据资源绑定，输入变化后旧验证结果失效。失败返回具体检查项和最小修复范围，修复后重跑受影响检查。

候选文件先校验再 promote。多文件提交记录逐文件状态与版本冲突；普通文件系统的多次 rename 不宣称跨文件事务原子性。部分提交失败时保留恢复清单，禁止粗暴覆盖用户后续修改。

## 16. G04：任务断点、副作用账本与恢复

现有会话检查点负责事件耐久；新增执行步骤账本负责“哪个动作可能已发生”，两者使用同一 taskId/stepId/executionId 关联，不重复保存原始大输出。

每个步骤至少记录 prepared、dispatched、running、effect_observed、verified、committed、failed、unknown 等事实及其时间、输入摘要和候选产物。分派前持久化意图，完成后持久化结果；崩溃发生在中间时恢复为 unknown，不能直接当作未执行。

恢复流程：

1. 加载任务与执行账本，核对输入版本、有效环境、权限和资源归属。
2. 向仍可连接的执行器查询 executionId；本地 PID 必须同时核对创建身份与归属，防止 PID 复用误杀。
3. 对已提交且验证身份一致的步骤复用结果；只读或明确幂等步骤可按策略重跑。
4. 未知写入、外部请求、安装或删除先查效果。适配器支持幂等键时复用同一逻辑操作键，不能每次重试生成新键。
5. 外部系统不支持幂等或结果查询时，明确需要核实，不能承诺任意任务恰好执行一次。

后台任务的进程内注册表增加持久“执行记录与恢复状态”，不承诺让任意操作系统进程在 Host 崩溃后原地续跑。可重新接管的托管进程需有生命周期协议；否则终止/核实后重建。重复通知和迟到回调不得覆盖已确认终态。

会话恢复、目标继续、定时唤醒和用户点击继续共用恢复入口。取消后的任务只有新的合法继续请求才恢复；后台或模型不能自行复活被用户取消的流程。

## 17. G05：本地 Agent 的真正远端执行

保留现有“访问远端独立 Harness”的 SSH 隧道入口，同时新增独立的远端执行 provider。两种模式在 UI、会话身份和缓存上明确区分。

本地 Agent 使用远端工作区时，文件、Shell、工具链、日志和候选产物的操作必须由远端 provider 执行。本地路径和宿主能力不能冒充远端路径及依赖；每个返回结果携带 hostId/backendId/contextId。

首个实现采用受控 SSH transport 加版本化执行 helper：握手确认 OS、架构、协议版本、工作区与支持能力；输入输出通过有界结构化帧承载 executionId、状态、数据和取消确认。子进程 stdout/stderr 作为数据帧传输，不能混入控制协议。

使用严格主机密钥校验和用户配置的认证，不转发本机模型凭据或 ssh-agent，不自动安装远端服务。缺少 helper 时返回具体准备要求；用户明确要求安装时走独立部署流程。

读写范围在远端独立执行授权和规范化检查，不能只在本机比较字符串。文件资源、工作目录、符号链接及临时目录按远端 OS 语义处理。数据下载、上传和正式交付有明确方向与版本校验。

断线后先查询原 executionId，不能重发命令。连接断开不等于任务失败或成功；无法确认进程状态时返回 unknown。取消必须确认远端收到并完成回收，超时则保留待核实状态。

容器或其他后端复用同一 provider 契约，分别验收；SSH 通过不能替代容器镜像身份、挂载及资源配额验证。

## 18. G06：应用级权限与 Computer Use 协议

在现有 Windows UIA、浏览器、UU 和动作审批上增加应用权限登记，不把文件目录授权当作桌面授权。

权限至少区分画面读取、输入操作、剪贴板读取、剪贴板写入、文件上传及高影响外部动作。支持允许一次、会话允许、用户主动保存的应用规则和撤销；已授权常规动作不重复打断。

应用身份结合主机、可执行文件身份、签名/包信息或浏览器 origin 等可验证属性；不能只凭窗口标题或显示名称授权。应用升级、身份变化和规则撤销重新检查，拒绝把旧规则套到同名进程。

撤销立即阻止新动作并取消待分派队列；已经发生的输入或外部提交不能宣称已回滚。人工接管期间暂停自动输入；交还控制权也不自动重做已经结束的任务。

模型原生 computer 协议使用明确的适配层连接动作、截图、错误和请求标识，验证坐标、目标换代、取消及错误恢复。函数工具名称类似不代表协议已兼容。

Windows、macOS、Linux 和远端桌面分别声明可用能力。缺少系统授权、锁屏、应用不可访问等情况保持明确状态，不能通过修改系统防护绕过。

## 19. G07：端到端能力评测与发行门禁

将既有单元、协议、模拟服务和实机测试接入同一个用例目录。每个用例描述前置环境、允许动作、输入、预期效果、禁止效果、验收器和清理策略。

固定任务集包括执行失败恢复、非默认路径软件发现、中文文件、文档转换、项目构建、工具加载与缓存、远端断线、桌面接管、任务恢复及多步骤产物交付。使用合成或经授权的测试数据，不依赖业务原件可随意修改。

按模型/提供方、OS/架构、Shell、后端、权限模式与二进制身份记录结果。模拟模型证明协议与工具行为；真实模型证明受测任务里的决策与恢复表现；真实账号、远端设备和桌面权限另行标注。

核心指标为任务真实成功率、误报成功率、未授权副作用、重复无效调用、恢复次数、模型请求数、总耗时与实际披露的成本。没有提供方用量不填零，没有原生平台执行不填通过。

严重正确性与授权用例出现一次确定失败即阻止发布；具有随机性的真实模型任务重复取样并记录全部结果，不挑选成功样本。性能比较使用同一任务集、相同环境和冷/热缓存条件。

测试失败关联到缺陷、修复和复测证据。确认的代码缺陷进入自动回归，不只写进经验记忆；相同基线已经通过的重测试不因文档或无关修改重复运行。

## 20. G08：经验到技能的受控改进

## 22. 集中实现、分层验证与提交推送

### 22.1 减少重复 Rust 编译

- 先确认当前基线、工作树改动归属、目标分支和现有缓存位置；不覆盖其他任务的未提交工作。
- 先完成接口、结构化结果、状态事件及测试用例设计，再集中完成相互依赖的 Rust、API、前端、配置迁移和文档修改。
- 日常修改阶段以代码审查、格式/静态检查、schema 校验和不依赖 Rust 重编译的测试发现低成本问题；不每改一个文件就 cargo build 或全量 cargo test。
- 复用同一个匹配工具链、target、profile 与 feature 组合的构建缓存；不运行无必要 cargo clean，不轮换 target 目录，不并发启动互相抢锁的构建。
- 代码基本收敛后，对受影响 crates 集中运行一次有针对性的 cargo check/test，再运行所需跨 crate 集成和发布门禁；测试构建可复用时不先重复做同配置的完整 build。
- 编译或测试失败后按根因批量修复，先重跑受影响检查；只有修改扩大影响范围或暴露新风险时才扩大复测范围。不能为减少编译次数而忽略必需的检查。

### 22.2 最终验证顺序

1. 核对全部 G01—G08 与 A01—A36 的实现状态、接口一致性、配置迁移、格式、静态检查和差异。
2. 完成受影响 Rust crates 的合并检查/回归；相同目标复用增量产物。
3. 使用一个已确认构建身份的候选二进制完成 Host、API、前端和真实多轮对话回归；修改前端后同步正式 dist/manifest，禁止混用旧资源。
4. 完成任务级效果核验、超时/取消/崩溃恢复和权限反向用例；核实所有测试后台进程与临时授权已收敛。
5. 修复发现的问题，再验证受影响范围。最终代码变化后，不能沿用已不匹配的旧二进制或旧测试结果。
6. Linux/macOS 等原生环境通过对应 CI 或实际测试环境完成；环境缺失记录为未验证，不冒充全平台完成。
7. 记录最终差异、测试命令、结果、未验证项和构建身份，再进入提交与推送。

### 22.3 提交与推送完整性

所有变更先完成统一审查和可本地完成的验证，修复失败后再提交。提交只包含本任务拥有的代码、必要锁文件、前端资源、迁移、回归和文档；不能用 git add -A 混入无关并行修改，也不能漏掉使功能实际生效的 Host 接线或发行资源。

提交前核对依赖和生成文件，提交后核对 commit 差异及工作树剩余变更。推送到已确认远端和分支，验证远端 commit 与本地提交一致；遇到远端更新正常整合，不通过强推覆盖他人工作。

如果平台 CI 必须在推送后运行，先推送验证分支触发 CI；CI 失败继续修复、复测并推送，全部必需门禁通过后才报告完整交付。这种验证分支推送不等于已经发布或完成验收。

最终报告分别写明：已实现、已验证、因外部条件未验证、提交 ID、推送目标和远端状态。不能将方案文档已合并、代码已提交、CI 已通过和安装版已升级混为一个完成状态。
