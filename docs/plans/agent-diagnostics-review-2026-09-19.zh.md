# 自动诊断、执行恢复与沙箱可靠性

适用版本：0.1.3-alpha.26。

## 故障根因

| 现象 | 已确认根因 | 实现行为 |
|---|---|---|
| 对话结束后内存持续增加 | Agent 派发缓存自引用、工厂残留实例，以及 GoalService 强缓存每代 Session 的完整历史 | 派发器按事件创建；按确切实例解除工厂持有；会话退役清除目标缓存，防止历史副本累积 |
| 小工作区正常，大仓库沙箱反复超时 | 每个新 AppContainer 身份都向整个工作区传播继承 ACL，并在退出时再次撤销；构建目录放大遍历成本 | 按目录文件身份和权限模式建立独立能力 SID；核验已有 ACL 后复用，运行器仅把当前模式对应的能力放入令牌 |
| 环境检查误报程序不可用 | 五秒预算覆盖了沙箱准备和程序执行全过程 | 分开等待权限准备、运行器 ready、程序探测；五秒只约束已启动的探测程序 |
| 超时后重试仍拖慢系统 | spawn_blocking 超时不会终止底层 ACL 工作，但旧实现丢弃等待句柄并允许再次创建线程 | 保留共享准备任务；相同目录和模式合并等待，最多两个权限工作线程并行 |
| PATH 中有 PowerShell/Python 却无法运行 | 自动发现选中 WindowsApps 应用执行别名 | 自动发现跳过别名；显式选择别名返回稳定错误码并保留选择，要求指定实际可执行文件 |
| 权限切换后连 read、grep 都被拒绝 | 验收契约环境守卫同时阻止只读取证 | 只读工具继续经过自身权限检查；环境守卫仅阻止受影响的写操作 |
| 未执行的操作被长期标成效果未知 | 账本没有区分工具体未调用、预检失败和已进入用户操作 | 注册表和执行适配器提供可信分派边界；未分派记录为 not_dispatched，已启动但效果不明仍为 unknown |
| 修改页面后刷新仍是旧界面 | 源码、正式 manifest、资源副本和运行程序不一致 | 发布资源由源码复制并计算哈希；技能版本 RPC 同时进入正式方法注册表 |
| 读取大日志时内存突然升高 | 输出虽有限额，读取阶段却先拼接全文 | 按流计数，只保存请求的行窗口和有界行前缀 |
| PowerShell 7 已发现却在沙箱中无法启动 | 私有安装目录缺少 AppContainer 读取权限，运行器仅识别 Python 运行库 | 按实际可执行路径识别完整 PowerShell 7 安装，仅赋予其运行库目录只读能力；工作区外读写仍受原边界限制 |
| 每一步都追加近似相同的运行上下文 | 工具列表来自 HashMap，顺序不稳定导致相同目录被识别为变化 | 对工具 schema 按名称排序，保持目录及模型请求头稳定 |
| 有技能却没有可用技能目录 | 动态技能提供者用“不完整”表示“不缓存”，导致整个目录发布被抑制 | 区分完整性与动态性；完整目录正常发布，动态适用条件每次重新检查 |
| 压缩失败后旧对话无法恢复 | 日志写入压缩重试、恢复、错误等事件，但读取器未登记这些事件 | 登记运行时实际产生的事件；未知未来事件继续拒绝，真实恢复错误保留原因 |

## 沙箱权限与启动证据

工作区能力按缓存位置、规范目录路径、卷及文件身份、只读/可写模式分别派生。只读和可写能力不能互换；访问权限仍由用户令牌与 AppContainer 能力共同限制，不授予 Everyone 或整用户目录权限。不同模式的 ACL 写入使用同一个目录锁，避免并发覆盖。

运行器报告 ancestors、workspace_permissions、read_permissions、runtime_permissions、process_creation 和 cleanup 阶段。启动超时携带最后阶段；程序运行超时与启动失败分别记录。权限准备超时后，后台工作仍受共享句柄和并发预算约束，重试不会增加同一准备任务。

Windows 本机对照结果：

| 场景 | 结果 |
|---|---|
| 小工作区 Node 版本探测 | 成功，约 0.30 秒 |
| 小工作区 Windows PowerShell 版本探测 | 成功，约 0.31 秒 |
| 大仓库逐进程 ACL 方案 | 300 秒内未确认 ready，停在 workspace_permissions |
| 大仓库首次能力准备 | 成功，100.672 秒 |
| 同一目录和模式再次执行 | 成功，0.125 秒 |
| 已建立可写能力后再次使用只读模式写文件 | EPERM，写入被拒绝 |
| 从授权工作区读取相邻未授权文件 | EPERM，访问被拒绝 |

首次准备大型目录仍可能较慢；复用消除了每条命令重复遍历目录的成本。缓存身份或 ACL 校验失败时重新准备或报错，不降级为无沙箱执行。

Windows ACL 传播行为见 [Microsoft：继承 ACE 自动传播](https://learn.microsoft.com/en-us/windows/win32/secauthz/automatic-propagation-of-inheritable-aces)；能力与令牌的共同访问约束见 [Microsoft：启动 AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer)。

## 验收契约与恢复

1. read、read_file、list_directory、glob、grep、环境探测及作业查询可以在当前权限下取证。
2. not_dispatched 表示可信调度记录证明请求操作没有进入执行；不与未知副作用混淆，也不永久阻塞最终内容验收。
3. unknown 保留原执行身份和证据。运行中的操作、部分失败、多步骤执行的早期效果不能通过口头声明清除。
4. 用户在任务验收页选择切换环境，提交精确契约版本。执行中的步骤会阻止迁移。
5. 环境迁移保留目标、约束、步骤和未知效果，清除旧验收结论、输出身份及技能验证证据；必须重新检查内容才能完成。
6. 完成操作再次核对环境，防止先验收、后切换权限而沿用过期结论。

## 自动诊断与工具恢复

诊断账本保存历史观察、验证及应用结果，不是当前缺陷计数器。历史 pending 记录不会因升级程序而批量变成 verified。

- ENVIRONMENT_VALIDATION_FAILED、ENVIRONMENT_PROBE_TIMEOUT、APP_EXECUTION_ALIAS_UNSUPPORTED 进入运行环境分类。
- FS_NOT_TEXT、IMAGE_FORMAT_UNSUPPORTED 提供文件类型和编码路由；read 支持显式 GB18030/GBK、UTF-16LE/BE，PDF 不再得到泛化的图片格式错误。
- COM_ACCESS_DENIED 区分自动化激活、文档打开与导出；不根据“拒绝访问”推断文件占用或授权状态。
- 非法 JSON 返回解析原因、行号和列号；不把所有语法错误压缩成“参数必须为对象”。
- 原生调用资源指纹包含 program 与 argv；不同程序参数的成功不能互相验证恢复。
- 重复失败提醒覆盖环境预检错误，提示核查阶段和新证据；改变命令文本不能修复相同的运行环境问题。
- 经验仍需通过既定恢复关联或人工验证，不能把任意后续成功当作环境故障已经修复。

## 发布与验收边界

源码测试、浏览器资源加载、WPS 实际导出、安装包身份分别提供证据。OOXML 结构检查不能替代 WPS 排版检查；源文件修改不能证明正在服务的页面已更新；注册表为空不能证明旧 Agent 已析构。

安装更新后必须由新进程承载修复。旧进程已经形成的引用关系和在途任务不会被磁盘上的新二进制自动改写。会话数据、诊断历史及用户凭据保留。
