# DSH 执行、升级与模型管理核查

验证日期：2026-09-11。Windows 运行版本：0.1.3-alpha.11。

核查范围为 Windows 本地执行链路、近期 32 个会话的 26,582 条存储记录、22 条诊断记录，以及模型请求与子 Agent 会话兼容逻辑。

## 代码缺陷与处理

| 问题 | 原因 | 处理后的行为 |
| --- | --- | --- |
| 简单命令等待 120 秒、PTY 无法启动 | 父目录被其他进程占用时，ACL 更新退回会递归传播的路径 | 祖先目录只修改自身权限；工作目录保留必要的继承处理 |
| 初始化与清理被误算作命令超时 | 宿主等待的是整个包装进程，而非实际命令的运行阶段 | 运行库准备、进程就绪、实际命令预算和包装进程回收分别处理；命令预算由 Windows 子进程等待控制 |
| 取消后轮询任务与等待计数残留 | 丢弃 Rust Future 不会自动取消已分离的 Tokio 任务，也不会执行 Future 内尚未运行的清理语句 | 作用域守卫撤销轮询任务、恢复取消信号、释放未轮询和已轮询的等待注册 |
| 前台执行被丢弃后进程继续存活 | 过程句柄由运行时保留，调用 Future 丢弃没有触发终止 | 前台调用取消或异常退出时终止所属进程树；正常后台作业继续由作业服务管理 |
| 异常终止遗留沙箱配置和权限 | 强制终止包装进程无法运行其 Rust 析构清理 | 普通命令超时保留包装进程执行清理；异常退出保留带校验和的归属记录，后续启动只回收已结束进程的专属权限，保留重定向目标文件 |
| 运行故障被压成通用工具错误 | PowerShell 丢弃沙箱事实；终端工具未传递底层错误码 | 区分沙箱初始化、权限拒绝、终端启动、命令超时、命令退出和用户取消，并保留错误原因 |
| 更换命令参数后继续重复同类失败 | 重复提醒插件未装入宿主，检测只比较完全相同的调用 | 宿主启用临时失败提醒；同一执行错误码可跨参数变化识别，用户新输入重置状态，提醒不改变授权边界 |
| 历史诊断笼统且难以定位 | 旧规则保存在账本中，未保留对应任务及调用标识 | 按可信错误码更新分类；新记录保留受限的任务、调用标识；运行诊断不作为长期模型经验复用 |

已存在的缓存请求修复和子 Agent 兼容修复一并进入验证范围：`prompt_cache_breakpoint` 使用对象格式，订阅接口保留其支持的缓存方式；会话读取识别 `execution/ultra-child`，继续拒绝其他未知且不可忽略的事件。

## 需要区别处理的历史记录

| 记录 | 结论 |
| --- | --- |
| `INVALID_REQUEST`，明确指出缓存断点收到布尔值 | 请求适配层格式问题，属于框架代码缺陷 |
| `SHELL_TIMEOUT`、终端启动超时 | 需要区分准备、命令运行与清理阶段；该会话已复现祖先 ACL 更新问题 |
| Git 目录错误、目标路径不存在、编辑匹配不唯一 | 应检查具体命令和目标，不能仅凭非零退出码认定运行框架损坏 |
| `TRANSPORT` | 连接或响应流失败；保留具体原因并按可重试条件处理 |
| HTTP 402、余额不足、账号使用额度耗尽 | 账号或服务条件，需要对应账号可用后继续 |
| UU 远端需要登录、解锁、连接归属未确认 | 远端状态或连接条件，需要人工完成必要操作；不自动绕过 |
| 用户拒绝、取消、手动接管 | 控制结果，不应记作模型回答错误 |

历史错误不因安装修复而自动标记“已恢复”。旧版本未留下可靠回收归属记录的系统配置不按名称批量删除。

## Codex 对照

Codex 的 Windows 执行器在启动完成后发送 `SpawnReady`，并对实际子进程执行等待和超时控制；错误包含执行阶段。其工具调度器只对明确的沙箱拒绝进入受审批策略约束的重试路径，其他错误保留原始失败，不统一作为可重试的沙箱问题。

DSH 采用相同的职责划分原则，使用本地就绪/超时通知、明确的错误码、受限的重试提示和作用域清理。现有的文件权限与审批策略继续生效。

依据：[Codex Windows 沙箱文档](https://learn.chatgpt.com/docs/windows/windows-sandbox)、[Windows 命令执行器](https://github.com/openai/codex/blob/94697375cb9d2aa8ae74d61957c6b396819bec94/codex-rs/windows-sandbox-rs/src/bin/command_runner/win.rs)、[工具调度与审批](https://github.com/openai/codex/blob/94697375cb9d2aa8ae74d61957c6b396819bec94/codex-rs/core/src/tools/orchestrator.rs)、[缓存参数规范](https://developers.openai.com/api/docs/guides/prompt-caching)。

## Token 消耗与 Codex 的差异

累计输入 token 是各次模型请求的合计，不能等同于当前上下文长度。一次任务经过多步工具调用，会多次携带此前的上下文。已确认会造成无效消耗的因素包括重复运行同一故障路径、错误的缓存断点请求、变化的提示词前缀，以及丢失或错误重放模型状态。

当前实现保留稳定会话缓存键、正确的显式断点对象，以及按提供方、实际端点、模型和账号隔离的 Responses 推理重放状态。新 Flash 的动态提示词更新由实际路由能力控制，切换不支持的路由、清空提示词或开始新序列时重新整理系统消息，避免旧规则复活。

实际远程桌面会话的重算结果为系统约 1,310 token、工具约 7,822 token、普通消息约 3,005 token。此前系统显示为零属于分类错误，并不表示系统指令没有发送。该会话的 12 次请求累计输入为 131,618 token，服务端在这 12 次记录中明确报告缓存读取为零；历史记录保持原样，不能以新代码推断过去已命中缓存。

Codex 还通过模型能力选择 Responses Lite、历史内工具定义、推理上下文和配置更新等协议能力。DSH 已接入按模型能力启用的 Responses Lite，具体请求范围见[能力说明](session-files-teams-and-network.zh.md)；不能把启用缓存键等同于复制了 Codex 的全部执行机制，也不能把历史缓存比率当作修复后的效果证明。缓存写入、读取、未披露统计与 ChatGPT 账号额度分别保留其含义。

依据：[OpenAI 缓存说明](https://developers.openai.com/api/docs/guides/prompt-caching)、[模型指导](https://developers.openai.com/api/docs/guides/latest-model)、[Codex 请求构造](https://github.com/openai/codex/blob/94697375cb9d2aa8ae74d61957c6b396819bec94/codex-rs/core/src/client.rs)。
